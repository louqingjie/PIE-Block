# 拓展板通信排障 Playbook

主控板 → 拓展板（UART1，P30/P31，230400 8N1，21 字节命令帧）这条链路不通时，
按下面顺序走，**不要先怀疑硬件/接线**：链路层能验证的先验证，再往载荷层收敛。

案例背景见 [SDCC 组帧低字节丢失](../pitfall/sdcc-组帧低字节丢失.md)。

## 触发信号

- 同一份固件源码，Keil 编译能正常控制拓展板，SDCC 编译不能。
- 或者：拓展板完全不动，但抓包能解出成帧。

## 前置条件

- USB 转串口接主控板 **P31（TX）+ GND**，串口助手开 **230400 / 8 / N / 1 / 无流控**。
- 需要看汇编时用随包工具链：`vendor/sdcc-toolchain/bin/sdcc(.exe)`。
- 需要样例固件时用生成器：`dart run packages/pieblock_core/tool/generate_smoke.dart <输出目录>`
  （产出 `debug.c` / `infantry.c` / `engineer.c` / `music.c`）。

## 步骤

### 1. 抓包，先只验帧边界

抓 P31，只看三件事：有没有 `AB BC` 帧头、有没有 `CD DE` 帧尾、每帧是不是 21 字节。

期望的帧结构：

```
AB BC <cmd> <p60 hi lo> <p62> <p64> <p66> <p74> <p75> <p76> <p77> CD DE
cmd：Init=0xAA  Duty=0xBB  Dir=0xDD
```

| 观察 | 判据 | 分支 |
| --- | --- | --- |
| 全是乱码，解不出 `AB BC` | 读取侧波特率/接线不对 | 换 230400 8N1、核对接线，回到第 1 步 |
| 边界正确、21 字节 | 链路层没问题 | 进第 2 步（问题在载荷） |

### 2. 载荷逐字节比对（两个编译器产物各抓一次）

重点看每个 16 位字的高/低字节是否**不同**。常见错法是低字节位置被写成高字节：

| 意图 | 正确 | 错法 |
| --- | --- | --- |
| Init 50Hz | `00 32` | `00 00` |
| Init 10000Hz | `27 10` | `27 27` |
| Duty 5000 | `13 88` | `13 13` |
| Duty 500 | `01 F4` | `01 01` |

出现 `hh hh` 这类「高低字节相同」→ 组帧取字节错，进第 3 步。

### 3. 最小复现：把可疑函数单独交给 SDCC

把出问题的组帧函数（或整个生成固件）编成汇编，参数从
`stc32g_sdcc/build_manifest.json` 的 `compile_flags` 抄：

```powershell
$sdcc = "vendor\sdcc-toolchain\bin\sdcc.exe"
& $sdcc -mmcs251 --model-large --stack-auto --opt-code-size --constseg CSEG -S `
  "-Istc32g_sdcc\include" "-Istc32g_sdcc\projects\ROBOMASTER_INFANTRY\inc" `
  "-Istc32g_sdcc\libraries\drivers\inc" "-Istc32g_sdcc\libraries\boards\inc" `
  "-Istc32g_sdcc\libraries\radio\inc" "<你的 main.c>"
```

注意：**SDCC 把 `.asm` 写进当前目录**，先 `cd` 到临时目录再跑，别把产物落在仓库根目录。

判读汇编：对同一 16 位字的两条落帧语句，看各自取的是不是不同字节——
正确应为一个 `>> 8` 的高字节 + 一个 `& 0xFF` 的低字节；若两次都只读元素首字节
（大端存储下即高字节），就是命中本类问题。

顺手看的两个信号：

- SDCC 输出 `DPTR no-match: cached=(#_x...) new=(#(_x...)` 警告 → 它的 DPTR 缓存优化在这段代码上失配。
- 出问题的写法特征：`uint16_t values[8]` + `control_frame_pack[3 + i*2]` / `[4 + i*2]` 这类**数组 + 表达式变址**。

### 4. 修复模板

不要用「数组 + 变址 + `>>8`/`&0xff`」的组合，改成逐字展开（与《RM电控指南》参考实现一致）：

```c
control_frame_pack[3] = (uint8_t)((p60 >> 8) & 0xFF);
control_frame_pack[4] = (uint8_t)(p60 & 0xFF);
/* …共 8 组… */
```

需要按**运行时下标**选通道时，用 `switch` 把 8 个分支展开，不要 `values[slot]`：

```c
switch (slot) {
case 0: ExpansionBoradControl(Duty_Change_Order, duty, 0, 0, 0, 0, 0, 0, 0); break;
/* …共 8 个 case… */
}
```

判据：重新编一次 `.asm`，同一 16 位字的两次落帧必须读到不同字节。

### 5. 上机复验

重新生成固件 → 烧写 → 抓 P31，应恢复成 `27 10`、`01 F4` 等正确配对，且拓展板动作正常。
把结论回填到对应的 pitfall 文档（记录「实机验证通过」）。

## 边界与相邻坑

- 本 playbook 只覆盖**固件侧组帧/取字节**类问题。若第 1 步就不过（乱码），是波特率/接线/主频问题，不属这里。
- 相邻已知坑：不要把栈上的帧数组当整帧指针传给别的函数，SDCC 的通用指针取数同样会生成错误字节（《RM电控指南》有记录）。
- 改生成器后必须同时跑：`dart analyze`、`dart test`，并在 `packages/pieblock_core` 重新 `generate_smoke` 核对产物。

## 归档约定

- 本目录（`docs/playbook/`）放**可复用的诊断流程**：触发信号 → 判定分支 → 手段 → 判据。
- `docs/pitfall/` 放**具体故障案例**：现象 → 根因 → 修复 → 规避，绑定具体版本/提交。
- 两者互链：playbook 只写「怎么查」，原理与取证写在 pitfall 里。
