# 主控板主频异常（33.1776MHz 校准值损坏）筛板流程

> 适用对象：STC32G12K128 主控板批量验收 / 维修复测。
> 目标：用**可重复、零风险**的方式把“主频异常”的板子从好板里挑出来，同时为后续阈值提供基线数据。

## 0. 现状更新（2026-10-23）

> 本文档第 1~8 节描述的是**故障发现与核实阶段**（当时固件标称 33.1776MHz）。
> 为解决该问题，固件已整体迁移到 **22.1184MHz**，改动清单、计算与验证记录见
> [主控板主频故障复盘与22.1184MHz迁移](../design/主控板主频故障复盘与22.1184MHz迁移.md)。

迁移后本手册的使用要点：

| 项 | 变化 |
|---|---|
| 固件标称主频 | **22.1184MHz**（`FOSC`、SDCC 延时计数、语音 Timer0 重载均已同步） |
| 阶段 1 判据 | **不变**：230400 能解出协议帧 = PASS（22.1184MHz 下 230400 仍精确整除） |
| 阶段 1 的“低档区间”解释 | 随标称频率变化：异常板会落在 `230400 × 实际主频 / 22.1184MHz` 附近，不再是 153k~167k |
| 阶段 2 的关键校准项 | 从 `CHIPID15`（33.1776 档）改为 **`CHIPID11`（22.1184 档）** |
| 探针固件 | 仍保留，用于**诊断**“33.1776 档校准值坏”的片子（历史坏板、或需要跑 33.1776 固件的场合），不作为交付固件 |

## 1. 现象与根因（本批已确认）

**现象**
- 同一份固件，个别板子串口波特率不对：按 230400 收发全是乱码，实测线上约 **153k~165k**；
- 固件里所有基于主频的延时同步变慢约 **1.46 倍**（例：3s 保持实测 4.39s）；
- STC-ISP 日志里硬件选项正常（“下次用户程序运行频率 33.178MHz”），**官方重烧 33.1776 也无效**；
- 同一份固件换到好板上完全正常。

**根因**
- 芯片出厂校准表里 **`CHIPID15`（33.1776MHz 档的 IRC 微调值）异常**：本例读到 `0x3D`；
- 同频段其它档实测刻度 `22.1184M=0x31、24M=0x54、27M=0x8A、30M=0xC2`，线性外推 33.1776MHz 应约 **0xFA**；
- 因为程序设频（`System_Clock_Set()`）和 STC-ISP 设频用的都是这个校准值，所以两条路都会落到 **≈22.6MHz**；
- 芯片其它频段正常（22.1184/24/27/30/35MHz 实测都准），属**芯片级校准数据缺陷**，软件无法可靠修复。

> **注（2026-10-23 更新）**：为规避该缺陷，固件已整体迁移到 **22.1184MHz**，详见
> [主控板主频故障复盘与22.1184MHz迁移](../design/主控板主频故障复盘与22.1184MHz迁移.md)。
> 因此下文“阶段 2 以 `CHIPID15` 为主判据”保留作历史参考；**当前固件前提下的关键校准项是 `CHIPID11`（22.1184MHz 档）**。

## 2. 判定标准

### 阶段 1：快速筛板（烧标准应用固件）

| 结论 | 判据 | 处置 |
|---|---|---|
| **PASS** | 230400 下解出 ≥10 个 21 字节协议帧，且是各候选档中最多的 | 通过 |
| **FAIL** | 230400 解不出，但 153k~167k 区间有 ≥10 帧 | 主频异常 → 进入阶段 2 定性 → 换片 |
| **WARN** | 有效帧太少 / 各档差异不明显 | 复核固件版本、接线、供电后重测，或直接进阶段 2 |
| **NO-SIGNAL** | 所有候选波特率 0 字节 | 查供电、CH340 的 RX 是否接主控 P31、是否共地、是否已烧应用固件 |
| **PROBE** | 收到探针固件的 ASCII 文本（含 ` A:` / `START`） | 先烧回标准应用固件再筛 |

### 阶段 2：探针定性（烧时钟自检探针固件）

| 结论 | 判据 |
|---|---|
| **PASS** | `CHIPID15 ≥ 0xE0` **且** 档 4（33.1776MHz）实测在 33.1776±8% 内 |
| **FAIL** | `CHIPID15 < 0xE0`，或档 4 实测偏差 >8% |
| **WARN** | 解不出探针报告行（探针未烧好 / 接线 / 供电问题） |

> 频率估计存在约 **±3% 的系统偏差**（串口分频与 CH340 量化所致），所以档位容差取 ±8%；
> **`CHIPID15` 是主判据**，它的好坏区间差距极大（0x3D vs ≈0xFA），不存在误判。

| 项目 | 说明 |

## 4. 阶段 0：构建探针固件（只需做一次）

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\diagnostics\build_clock_probe.ps1
```

产物：`tools/diagnostics/clock_probe_keil.hex`（`*.hex` 已在 .gitignore 中，不会入库）。
脚本原理：临时复制 `stc32g/Libraries` 与 `stc32g/Projects/ROBOMASTER_INFANTRY`，用
`tools/diagnostics/clock_probe_main.c` 覆盖 `USER/src/main.c`，调用 `UV4 -r` 全量重建，**不改动仓库工程文件**。

探针固件行为（烧完后）：
1. 先执行与应用固件相同的 `Board_Init()`（即按标称 33.1776MHz 设频）；
2. 打印两行 `I A:xx V:xx B:xx D:xx T:xx R:xx`
   （A=IRTRIM、V=VRTRIM、B=IRCBAND、D=CLKDIV、T=**CHIPID15**、R=CHIPID23）；
3. 打印 `START`，进入 7 档循环：`0`=22.1184M、`1`=24M、`2`=27M、`3`=30M、
   `4`=33.1776M（手册写法）、`5`=35M、`6`=33.1776M（应用写法），
   每档打印一行报告 + 连发 240 个档号字符。
4. 线上波特率 = `230400 × 实际主频 / 33.1776MHz`，所以“某档字符在哪个波特率能解出”就代表该档真实主频。

## 5. 阶段 1：快速筛板（每板约 2 分钟）

1. 烧**标准应用固件**（IDE 正常流程或 STC-ISP 均可）；
2. 断电再上电，接好 CH340（RX→P31、共地）；
3. 运行：

```powershell
.\.venv\Scripts\python.exe tools\diagnostics\board_clock_screen.py COM3 --json 记录\板号-阶段1.json
```

4. 按输出记录结论与退出码（0=PASS、1=FAIL、2=WARN、3=NO-SIGNAL、4=PROBE）。

**批量执行（推荐，自动写 CSV）**：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\diagnostics\run_screen_batch.ps1 -Stage 1
```

脚本会逐块提示“接好板子后按回车”，自动跑检测、把结论写进
`tools/diagnostics/screen_results.csv`（板号、时间、结论、估计主频、原因等），输入 `q` 结束。

## 6. 阶段 2：探针定性（每板约 1.5 分钟）

1. STC-ISP 烧 `tools/diagnostics/clock_probe_keil.hex`：
   - 芯片型号 **STC32G12K128**
   - 频率 **33.1776MHz**，选“不调节/使用内部预置频率”
   - **勾选“本次下载需要修改硬件选项”**
   - 冷启动下载；烧完断电再上电
2. 运行：

```powershell
.\.venv\Scripts\python.exe tools\diagnostics\board_clock_probe_report.py COM3 --json 记录\板号-阶段2.json
```

批量执行同理（会记录 `CHIPID15/CHIPID23` 与各档实测）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\diagnostics\run_screen_batch.ps1 -Stage 2
```

3. 记录：`CHIPID15`、`CHIPID23`、各档实测估计、结论。

## 7. 阈值与基线（重要）

- **暂定阈值**：`CHIPID15 < 0xE0` 判“校准值异常”（针对 33.1776MHz 标称）；
  迁移到 22.1184MHz 后应改用 **`CHIPID11`** 作主判据，阈值需重新采集基线确定；
- **建议先建基线**：拿 **≥5 块已知好板**跑阶段 2，记录 `CHIPID15` 的 min/max，再据此收紧阈值（例如好板都在 0xF8~0xFF，则可把阈值提到 0xF0）；
- 参考刻度（本批坏板实测，供人工比对）：

| 档 | 目标 | 该档写/读到的 IRTRIM | 实测主频 |
|---|---|---|---|
| 0 | 22.1184M | 0x31 | ≈22.1M ✅ |
| 1 | 24M | 0x54 | ≈24M ✅ |
| 2 | 27M | 0x8A | ≈27.5M ✅ |
| 3 | 30M | 0xC2 | ≈30M ✅ |
| 4 | 33.1776M | 0x3D（= CHIPID15，异常） | **≈23.0M ❌** |
| 5 | 35M | 0x50 | ≈35M ✅ |
| 6 | 33.1776M（应用写法） | 0x3D | **≈23.0M ❌** |

## 8. 记录表字段（建议 CSV）

```
板号, 日期, 测试人, 阶段1结论, 230400帧数, 低档帧数, 估计主频MHz,
```

## 9. 注意事项（务必遵守）

1. **不要把“运行时测频 + 自动改正波特率”写进正式固件**：32K 唤醒定时器等内部基准精度有限
   （±1~3% 且温漂大），一旦用来改正所有板子，会把基准不准的好板一起改坏；
2. 探针固件**只用于诊断**，不得作为交付固件；
3. 阶段 1 的判据（230400 正常 = PASS）在 22.1184MHz 标称下**依然成立**（波特率仍精确 230400）；
   但“低档区间 = 异常”的具体波特率随标称频率变化，**更换编译频率时必须同步修改**
   `board_clock_screen.py` 的候选波特率与判定说明；
4. `CHIPID15` 异常属芯片级缺陷，**交付前应换片**；软件兜底（如外推 IRTRIM）只能救急，
   且脱离出厂校准点，温漂/一致性无保证；
5. 探针会初始化串口并发大量数据，属正常现象；测试完记得把板子烧回应用固件。

## 10. 已确认案例

- 本批 1 块坏板：阶段 1 在 **157300** 解出协议帧、230400 无帧；阶段 2 读到
  **CHIPID15 = 0x3D**，档 4/6 实测 **≈23.0MHz**，其余档全部正常 → 判定芯片校准数据损坏。
- 好板侧数据待补：建议用 ≥5 块好板跑阶段 2，补齐 `CHIPID15` 基线后更新第 7 节阈值。
