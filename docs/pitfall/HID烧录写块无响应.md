# USB-HID 烧录在第二块（0x0080）设备无响应

一次实机问题的记录：`info → unlock → erase` 与首块 `0x0000` 全部正常，紧接着的
第二块 `0x0080` 收不到任何回包，整个烧录中断。

> 协议与命令表见 [HID_PROTOCOL.md](../../stc32g/toolchain/stcflash/HID_PROTOCOL.md)，
> 用户侧操作说明见 [Flutter 编译与烧录指南](../guides/Flutter编译与烧录指南.md)。

## 现象

应用「进度与日志」页状态栏：

```text
Bad state: 写入 0x0080：设备无响应
```

同一份日志里，一次 332 块的烧录停在第二块：

```text
正在校验待烧录固件…
正在连接主控板引导程序…
正在擦除主控板程序区…
正在写入固件 1/332
（随后报错：写入 0x0080 无响应）
```

要点：

- 设备是活的 —— `info`/`unlock`/`erase` 与首块 `0x0000`（cmd `0x32`）都拿到了 `02 54`。
- 失败的是**首块之后的第一个后续块**（`0x0080`，cmd `0x12`），地址、命令、数据长度
  都与已验证的参考实现逐字节一致。
- 复现稳定：连续两次点击「烧录当前固件」，都停在同一个地址。
- 状态栏显示的是 Dart 运行时前缀 `Bad state: `，看不出下一步该做什么。

## 证据

对照已验证的参考实现 `stc32g/toolchain/stcflash/pie_block_hid.py`（真机烧录通过）
与 Dart 移植 `packages/pieblock_hid/lib/src/protocol.dart`：

| 环节 | 参考实现 | Dart 移植（修复前） |
| --- | --- | --- |
| 帧内 64 字节报告 | 每报告之间 `time.sleep(0.001)` | 三份报告连续写，无间隔 |
| 块写失败 | 抛错退出 | 抛错退出 |
| 失败提示 | `写块 @0x%04X 无响应` | `StateError` → 界面显示 `Bad state: …` |

也就是说，Dart 侧唯一与「能跑通」的实现有差异的地方，就是帧内报告之间没有留间隔。
设备固件按帧长度字段跨报告重组：写入命令帧是 141 字节（`64/64/13` 三份报告），
报告贴得太紧时设备会丢掉整帧，读超时 3s 后返回空。

设备丢帧窗口出现在「刚回完上一块 ACK、正在编程 flash」的时候，所以第一块正常、
第二块开始失败；即使丢帧，重发同一块也是安全的（按地址写块幂等）。

## 修复（第一轮：Dart 侧节奏与重发）

1. `protocol.dart`：恢复参考实现的 1ms 帧内报告间隔（`hidReportGap`），并把
   「设备无响应」从 `StateError` 拆成 `HidNoResponseException`，便于只对这一类
   失败做重试。
2. `flasher.dart`：写块时对无响应按同一地址重发（默认 3 次，间隔 50ms）；连续
   失败后先用只读的 `info` 探活，再按结果给出「仍在 ISP 模式，直接重试」或
   「断电重新上电后重试」的中文指引；状态栏不再出现 `Bad state:` 前缀，完整指引
   同时写进日志区。
3. 单测覆盖：帧内间隔、丢一帧后自动重发并烧完、连续无响应时的失败文案与探活分支。

## 第二轮：Linux 实机复测暴露写语义差异

装好第一轮修复后在同一台 Linux 机器上复测（ROBOMASTER_INFANTRY，52392 字节 /
414 块）：

```text
正在写入固件 129/414
写入 0x4080 无响应，正在重发（第 2/3 次）
写入 0x4080：写入报告失败
```

两个新事实：

- 失败点从**第 2 块**退到**第 130 块**才出现（两次复现分别是 0x0080 与 0x4080，
  说明丢帧是概率性的、与地址无关）。1ms 帧内间隔把丢帧率压下来了一个量级，
  但没有根治。
- 重发时连报告都发不出去（`写入报告失败`），说明**内核对中断 OUT 的写入本身
  失败了**，而不是设备慢。

根因（Linux 侧）：`hidraw` 的 `::write` 是异步的，只把报告交给 usbhid 的中断
OUT URB；设备还在忙（正在编程 flash、上一份报告还没被收下）时内核**立即返回
`-EBUSY`，这份报告根本不会发出去**。而 Windows 的 `pb_hid_write` 是
`WaitForSingleObject(overlapped.hEvent, 2000)`——等这一份报告真正上总线才返回，
所以同一份 Dart 协议层在 Windows 上不会踩到丢报告的问题。换言之：Linux 侧
「写成功」并不等于「设备收下了报告」，大帧的中间报告被静默丢掉，设备就永远凑不齐
一帧（表现为整帧无响应）。

### 修复（第二轮：Linux 写语义对齐）

- `pieblock_hid_hidraw.cpp`：`pb_hid_write` 对「设备忙」的瞬时错误
  （`EBUSY`/`EAGAIN`/`EINTR`/`ETIMEDOUT`）做与 Windows 等价的**有界退让重试**
  （2000ms 窗口、1ms 间隔），只有报告被内核收下才返回成功；其它错误立即失败。
  重试不持全局锁。
- `flasher.dart`：写块阶段的**任何**失败（不只是无响应）都走同一套收尾——探活 +
  块号 + 「仍在 ISP 模式可直接重试」/「断电重新上电后重试」，不再只丢一行
  `写入报告失败`。
- 单测补充：写报告失败时的块号与指引文案。

## 第三轮：写语义修复生效后，墙退到固定位置

带第二轮修复（写报告忙重试）重新构建 Linux 版复测，日志：

```text
正在写入固件 129/414
写入 0x4080 无响应，正在重发（第 2/3 次）
第 130/414 块（写入 0x4080：写入报告失败）：写入中断，烧录中断
主控板已无响应：请关闭四个开关，给主控板断电几秒后重新上电…
```

- 已确认这次跑的是新库：`build/linux/x64/debug/bundle/lib/libpieblock_hid.so`
  的 mtime 晚于提交时间，反汇编 `pb_hid_write` 能看到 `IsTransientWriteError`
  与 `usleep` 重试循环。
- 失败点**两次都精确停在第 130 块（0x4080）**，与地址无关的「概率丢帧」已经
  不成立——这是**确定性**的墙；第一轮的 1ms 间隔确实消掉了此前的第 2 块失败。
- 重发时报告写不进去、连只读的 `info` 探活也没有回应 ⇒ 设备这一侧已经不再
  收发，而不是主机「忙」。
- 0x4080 的块内容（112 字节真实数据 + 7 个 0x00 + 9 个 0xFF）与相邻块没有
  结构性差异，排除「空块/特殊内容」这类猜测。

剩下的问题变成：这堵墙是**设备/会话级**（约 1 秒或约 130 块后 ISP 会话失效、
或端点停住），还是**主机 USB 栈**（端点错误状态）。两者都只能靠外部证据区分。

### 配套工具（Linux）

- 新增 `stc32g/toolchain/stcflash/linux_hidraw_flash.py`：零依赖（hidraw +
  ioctl）的 Linux 烧录/诊断脚本。`--probe-only` 判断板子此刻是否还在 ISP 并
  会回话；`--report-gap-ms` 用来做「改变节奏看墙是否跟着移动」的受控实验
  （若把间隔调到 20ms 后失败点掉到个位数块，说明墙跟时间有关；仍停在第 130 块
  则说明跟块数/地址有关）；`--no-erase --start-block N` 可以断电重新上电后
  从断点续烧，已写入的块不会被擦掉；每块都打印累计用时。
- 新增 `packages/pieblock_hid/tool/dump_block_plan.dart`：打印 HEX 的烧录计划
  （索引/命令/地址/块数据 sha1），已与上述脚本 `--dry-run` 对拍过 52392 字节
  的步兵固件，414 块逐行一致。
- 下一步取证：失败瞬间的 `sudo dmesg -T | tail -50`（是否出现 USB 断开/重枚举）
  与失败后立刻 `lsusb -d 34bf:1001`（设备是否还在总线上）；必要时用 `usbmon`
  抓包（仓库现有 `analyze_capture.py` 只认 Windows 的 USBPcap 格式）。

## 规避要点

- **不要删掉帧内报告间隔。** 参考实现的 1ms 是有意留的（不是"USB 流控能兜住"就能省），
  大帧拆报告发送时必须逐报告留出间隔。
- **Linux 的 hidraw 写是异步的，不能把 `write` 成功当作"设备已收到"。** 必须像
  Windows 那样对设备忙的 `-EBUSY` 做有界退让重试，否则大帧会被静默截断。
- 写块是幂等的：设备无响应时先原样重发，不要立刻让用户重新上电。
- 擦除之后设备一旦掉线就再也接不上，所以重发只针对写块，不要自动重跑整条流程。
- 失败提示要能指导操作：区分「仍在 ISP 模式」与「已退出 ISP」，并说明「用同一份
  固件重试、无需重新编译」。
