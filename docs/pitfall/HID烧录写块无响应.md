# USB-HID 烧录在第二块（0x0080）设备无响应

一次实机问题的记录：`info → unlock → erase` 与首块 `0x0000` 全部正常，紧接着的
第二块 `0x0080` 收不到任何回包，整个烧录中断。

> 协议与命令表见 [HID_PROTOCOL.md](../../stc32g/toolchain/stcflash/HID_PROTOCOL.md)，
> 用户侧操作说明见 [Flutter 编译与烧录指南](../guides/Flutter编译与烧录指南.md)。

## 现象

应用「进度与日志」页状态栏：

```text
Bad state: 写入 0x0080：设备无响应
```

同一份日志里，一次 332 块的烧录停在第二块：

```text
正在校验待烧录固件…
正在连接主控板引导程序…
正在擦除主控板程序区…
正在写入固件 1/332
（随后报错：写入 0x0080 无响应）
```

要点：

- 设备是活的 —— `info`/`unlock`/`erase` 与首块 `0x0000`（cmd `0x32`）都拿到了 `02 54`。
- 失败的是**首块之后的第一个后续块**（`0x0080`，cmd `0x12`），地址、命令、数据长度
  都与已验证的参考实现逐字节一致。
- 复现稳定：连续两次点击「烧录当前固件」，都停在同一个地址。
- 状态栏显示的是 Dart 运行时前缀 `Bad state: `，看不出下一步该做什么。

## 证据

对照已验证的参考实现 `stc32g/toolchain/stcflash/pie_block_hid.py`（真机烧录通过）
与 Dart 移植 `packages/pieblock_hid/lib/src/protocol.dart`：

| 环节 | 参考实现 | Dart 移植（修复前） |
| --- | --- | --- |
| 帧内 64 字节报告 | 每报告之间 `time.sleep(0.001)` | 三份报告连续写，无间隔 |
| 块写失败 | 抛错退出 | 抛错退出 |
| 失败提示 | `写块 @0x%04X 无响应` | `StateError` → 界面显示 `Bad state: …` |

也就是说，Dart 侧唯一与「能跑通」的实现有差异的地方，就是帧内报告之间没有留间隔。
设备固件按帧长度字段跨报告重组：写入命令帧是 141 字节（`64/64/13` 三份报告），
报告贴得太紧时设备会丢掉整帧，读超时 3s 后返回空。

设备丢帧窗口出现在「刚回完上一块 ACK、正在编程 flash」的时候，所以第一块正常、
第二块开始失败；即使丢帧，重发同一块也是安全的（按地址写块幂等）。

## 修复

1. `protocol.dart`：恢复参考实现的 1ms 帧内报告间隔（`hidReportGap`），并把
   「设备无响应」从 `StateError` 拆成 `HidNoResponseException`，便于只对这一类
   失败做重试。
2. `flasher.dart`：写块时对无响应按同一地址重发（默认 3 次，间隔 50ms）；连续
   失败后先用只读的 `info` 探活，再按结果给出「仍在 ISP 模式，直接重试」或
   「断电重新上电后重试」的中文指引；状态栏不再出现 `Bad state:` 前缀，完整指引
   同时写进日志区。
3. 单测覆盖：帧内间隔、丢一帧后自动重发并烧完、连续无响应时的失败文案与探活分支。

## 规避要点

- **不要删掉帧内报告间隔。** 参考实现的 1ms 是有意留的（不是"USB 流控能兜住"就能省），
  大帧拆报告发送时必须逐报告留出间隔。
- 写块是幂等的：设备无响应时先原样重发，不要立刻让用户重新上电。
- 擦除之后设备一旦掉线就再也接不上，所以重发只针对写块，不要自动重跑整条流程。
- 失败提示要能指导操作：区分「仍在 ISP 模式」与「已退出 ISP」，并说明「用同一份
  固件重试、无需重新编译」。
