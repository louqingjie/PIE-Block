# AI 改动提案：提案-确认流程

AI 要改工程，但又不能和用户在 GUI 里的编辑互相覆盖。MCP 下架后，CLI 是唯一的 AI 入口，
而 CLI 直接写 `.pieproj` 会和应用的自动保存打架：应用内存里的文档会在 500ms 防抖后
把磁盘上的外部改动整体覆盖掉。

本文记录采用的方案：**AI 只提交提案，应用是工程文件的唯一写者**。

## 为什么不是「锁 UI」或「文件监听」

- **锁 UI**：需要 AI↔应用之间的实时通道（MCP 刚被移除），还要处理 AI 崩溃、超时、用户
  被锁死等失败模式，代价远大于收益；
- **文件监听 + 冲突提示**：只能“发现”冲突，不能避免；两个进程的「读 → 改 → 写」之间
  仍然存在覆盖窗口，需要哈希基线 + 短写锁才能闭环；
- **提案-确认**：把写者收敛到应用一个进程，冲突从根上不存在；代价是用户要点一下“应用”。

## 流程

```text
AI                     CLI                        应用（唯一写者）
 │ 读 robot.pieproj      │
 │ 复制/修改候选          │
 ├─────────────────────► propose robot.pieproj --config candidate.pieproj
 │                      │ 校验 + 往返核对 + diff
 │                      ├── 写 robot.pieproj.proposed（原子替换）
 │ ◄── stdout JSON ─────┤
 │                      │        轮询发现提案（1.5s）
 │                      │        ├─ 顶部横幅：查看 / 应用 / 丢弃
 │                      │        ├─ 用户「应用」→ AppController.applyProposal
 │                      │        │   └─ 写 robot.pieproj（原子）、可一步撤销
 │                      │        └─ 写 .result、删除提案
```

- 提案与工程同目录：`<工程完整路径>.proposed`；
- 应用同一时间只处理一份待确认提案；新提案需要 `--force` 覆盖；
- 应用不自动应用提案，也不锁定编辑界面。

## 提案文件格式

```json
{
  "schema": 1,
  "kind": "pieblock-proposal",
  "baseSha256": "<工程文件内容的 SHA-256>",
  "createdAt": "2026-11-18T06:30:00.000Z",
  "tool": "pieblock-cli/1.0.0",
  "changedPaths": ["chassis.normal_speed"],
  "document": { "format_version": 23, "project_kind": "infantry", "config": { } }
}
```

- `baseSha256` 让应用判断「提案生成后工程是否又被保存过」，展示「基于旧版本」警告；
- `changedPaths` 只是摘要，应用展示差异时会用同一套 diff 重新计算；
- `document` 是完整工程 JSON，应用只取其中的 `config`，`guide_progress`、`created_at`
  等用户侧状态保持当前值。

## 拒绝规则

CLI 在落盘提案之前做四道检查，任何一道失败都不会留下提案文件：

1. **结构**：必须是完整且可解析的 `.pieproj`，格式版本在支持区间；
2. **类型一致**：候选的 `project_kind` 必须与目标工程相同；
3. **往返核对**：候选 JSON 里出现的每个字段，经项目模型解析后必须读回同值。枚举拼错
   被静默回退、未知字段、类型强转都会在这里被拒绝并给出字段路径——这是 MCP 时代
   `propose_patch` 的核心保护，现在移到 CLI；
4. **不新增错误**：候选不得引入新的 error 级校验问题（按「字段路径 + 错误文案」比较）。
   工程本来就处于「配置到一半」的状态时，既有错误允许保留——AI 只对「让工程变差」
   负责，不要求它先把无关字段填完；应用侧会提示应用后仍剩多少错误。没有差异也拒绝。

退出码：结构/IO 问题 3，其余拒绝 2，已有待确认提案 6。

## 应用侧状态

| 状态 | 含义 | UI |
| --- | --- | --- |
| `none` | 没有提案 | 不显示 |
| `pending` | 提案可应用 | 横幅 + 查看/应用/丢弃 |
| `invalid` | 提案损坏、类型不符或校验失败 | 横幅提示错误 + 丢弃 |

`pending` 额外带两个标记：

- `stale`：`baseSha256` 与当前工程文件不一致（提案基于旧版本）；
- `dirty`：内存文档与磁盘不一致（用户有未保存改动）。

还有一个 `remainingErrors` 计数：工程本身没配置完时，提案允许保留既有错误，应用侧
把「应用后仍剩几个错误」显示在横幅和差异对话框里，避免用户误以为应用后工程就可用了。

两者都只警告、不阻止应用；用户确认后应用会重新解析校验一次。

## 失败与边界

| 情况 | 行为 |
| --- | --- |
| AI 中途崩溃 | 提案留在磁盘，最多一份；用户可丢弃 |
| 应用没打开 | 提案留在磁盘，下次打开工程时出现 |
| 应用写盘失败 | 保留提案、状态不变、提示错误，可重试 |
| 应用崩溃（写后删前） | 提案变 stale，用户可丢弃 |
| 提案删除失败 | 记住哈希，本次会话不再提示同一份 |
| Web / Android content URI | 不启用提案检测 |
| 用户再次编辑 | 上一份提案的「撤销」快照失效 |

## 后续可加

- CLI `--set path=value` 的增量提案（免去复制整个工程）；
- `propose --wait` 读取 `.result`，把「用户应用/丢弃」回传给 Agent；
- 应用侧把 `*.proposed.result` 清理策略（当前覆盖写）。
