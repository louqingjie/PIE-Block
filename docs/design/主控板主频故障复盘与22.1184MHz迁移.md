# 主控板主频故障复盘：33.1776MHz 校准值异常与 22.1184MHz 迁移

> 时间：2026-10-22 ～ 10-23
> 对象：STC32G12K128 主控板（1 块故障板 + 1 块好板对照）
> 固件：SDCC 与 Keil C251 两套运行时（`stc32g_sdcc/` 与 `stc32g/`）
> 相关文档：[主控板主频异常筛板流程](../playbook/主控板主频异常筛板流程.md)（发现/核实/筛板手册）

## 1. 结论摘要

| 项 | 内容 |
|---|---|
| **现象** | 同一份固件，故障板串口实测约 153k~157k（应为 230400），固件内所有 `Ms_Delay` 同步变慢约 **1.46 倍**（3 s 保持实测 4.39 s） |
| **实际主频** | **≈22.6 MHz**（由延时比例 1.4645 反推：`33.1776 / 1.4645 ≈ 22.65`） |
| **根因** | 该芯片出厂校准表 **`CHIPID15`（33.1776MHz 档 IRC 微调值）异常 = `0x3D`**；同频段其它档刻度外推，该值应约 **`0xFA`** |
| **为什么改不动** | 程序 `System_Clock_Set()` 与 STC-ISP 下载写选项读的都是这个校准值，两条路都落到 ≈22.6MHz，所以“官方重烧 33.1776”也无效 |
| **性质** | 芯片级校准数据缺陷（同芯片 22.1184/24/27/30/35MHz 实测全部正常），软件无法可靠修复 |
| **解决** | 全系统编译主频 **33.1776MHz → 22.1184MHz**（该档校准正常，且 `22.1184e6/4/230400 = 24` 整除），并重算 SDCC 延时计数与语音 Timer0 重载 |
| **验证** | SDCC 16 个工程构建 PASS、Keil 工程 0 Error；故障板标定固件 `1000/3000/10/1000 ms` 实测 `1007.4/3022.8/9.8/1007.5 ms` |

## 2. 发现与核实过程（证据链）

### 2.1 初始现象
用户贴出一段“主控板发给拓展板”的串口序列，按 230400 解码后字节重复、字段异常。实际是**串口按 230400 去读一条 ~153.6k 的线路**，属解码假象。

### 2.2 排除软件因素
| 证据 | 结论 |
|---|---|
| 同一份 hex 在好板上 230400 正常 | 固件/编译器/烧录工具均无问题 |
| 故障板换用官方 STC-ISP、用户自研烧录器结果相同 | 排除烧录链路 |
| 在故障板对应 hex 中确认存在时钟设置机器码（`CLKDIV=4 → 读 CHIPID15→IRTRIM → 读 CHIPID23→VRTRIM → IRCBAND=2 → CLKDIV=0`） | 排除“设频代码没编进去” |
| 硬件选项日志显示“下次用户程序运行频率 33.178MHz”，重写仍无效 | 排除“选项没写进去” |

### 2.3 量化实际主频
从抓到的协议帧时间戳测量固件延时（`Ms_Delay` 由固定指令数循环实现，与编译器无关）：

| 固件延时 | 标称 | 实测 | 比例 |
|---|---|---|---|
| `duration_ms`（Duty 置位→归零） | 3000 ms | **4393.6 ms** | 1.4645 |
| `TEST_GAP_MS` | 1000 ms | **1464.8 ms** | 1.4648 |
| 单轮循环 | — | 6.690 s（稳定重复） | — |

→ `实际主频 = 33.1776 / 1.4646 ≈ 22.65 MHz`；与线上波特率 `230400 × 22.65/33.1776 ≈ 157k` 相互印证。

### 2.4 探针固件定性（关键一步）
烧“时钟自检探针”（7 档切换 + 寄存器回读），在故障板上得到：

| 档 | 目标频率 | 写入/读回 IRTRIM | 期望波特率 | 实测命中 | 结论 |
|---|---|---|---|---|---|
| 0 | 22.1184M | `0x31` | 153600 | 150k~164k | ✅ 准 |
| 1 | 24M | `0x54` | 166667 | 162k~178k | ✅ 准 |
| 2 | 27M | `0x8A` | 187500 | 186k~202k | ✅ 准 |
| 3 | 30M | `0xC2` | 208333 | 204k~226k | ✅ 准 |
| **4** | **33.1776M** | **`0x3D`（= CHIPID15）** | 230400 | **152k~168k** | ❌ 实跑 ≈22.9M |
| 5 | 35M | `0x50` | 243056 | 236k~252k | ✅ 准 |
| **6** | 33.1776M（照抄应用写法） | `0x3D` | 230400 | 152k~168k | ❌ 同上 |

寄存器读数：`CHIPID15 = 0x3D`、`CHIPID23 = 0x1A`、`VRTRIM=0x1A`、`IRCBAND=0x02`。

### 2.5 根因判定
同一频段（27M 频段）实测刻度：

```
22.1184M ← 0x31(49)
24M      ← 0x54(84)
27M      ← 0x8A(138)
30M      ← 0xC2(194)
33.1776M ← 芯片给的是 0x3D(61)   ← 比 22.1184M 的 0x31 只高一点，明显错误
```

按刻度线性外推，33.1776MHz 应在 `0xFA` 附近（该档已接近 27M 频段上限）。**芯片把 33.1776MHz 档的校准值写坏了**，因此任何“设成 33.1776”的路径都会落到 ≈22.6~23MHz。

### 2.6 为什么不做“运行时自测主频 + 自动改正”
- 读 CHIPID 不是测量（本次故障恰恰是标称值坏了）；
- 内部可用的独立基准只有 32K 低速振荡器/掉电唤醒定时器，精度约 ±1~3% 且温漂大；
- 若用它给所有板子重算波特率/延时，会把“基准不准的好板”一起改坏 —— **明确不写入正式固件**（筛板文档第 9.1 条已记录该决策）。

## 3. 解决方案：迁移到 22.1184MHz

### 3.1 选型对比

| 候选 | 230400 精度 | 其它常用波特率（9600/115200/460800/921600） | 相对 33.1776 速度 | 本批芯片校准 | 结论 |
|---|---|---|---|---|---|
| 33.1776M（原） | 精确 | 全部整除 | 1.00× | ❌ CHIPID15 坏 | 不可用 |
| **22.1184M** | **精确**（24 分频） | **全部整除** | 0.667× | ✅ CHIPID11 正常 | **选用** |
| 24M | +0.16%（26 分频） | 不整除 | 0.723× | ✅ CHIPID12 正常 | 备选 |
| 44.2368M | 精确（48 分频） | 全部整除 | 1.33× | 未验证 | 高频段风险大，不选 |

22.1184MHz 与 33.1776MHz 同属 27M 频段，`System_Clock_Set()` 里现成有 `case 22118400`，改动最小、余量最大。

### 3.2 改动清单（本次已实施）

| 文件 | 改动 |
|---|---|
| `stc32g_sdcc/include/common.h` | `FOSC 33177600UL` → `22118400UL` |
| `stc32g_sdcc/startup/common.c` | 3 处 `#if defined(__SDCC) && (FOSC == 33177600UL)` → `22118400UL`；**`Register_Set()` 内 `#if (33177600 == FOSC)` → `22118400`（不改则根本不调用 `System_Clock_Set()`）**；`Delay1000us_Reference` 计数 `0x2065(8293)` → `0x1599(5529)`；`Delay1us_Reference` 计数 `0x0007(7)` → `0x0005(5)` |
| `stc32g/Libraries/startup/inc/common.h`（Keil） | `FOSC 33177600//24MHz` → `22118400//22.1184MHz` |
| `stc32g/Libraries/startup/src/common.c`（Keil） | `#if (33177600 == FOSC)` → `#if (22118400 == FOSC)`（Keil 延时用 `DELAY_MS/DELAY_US` 自适应，无需改数值） |
| `stc32g_sdcc/projects/BUZZER_VOICE_SMOKE/src/main.c` | `VOICE_TIMER_RELOAD 60928U` → `62464U`（`65536-3072`，仍 7200Hz）；载波说明按 `FOSC/64800 = 341` 修正 |
| `stc32g_sdcc/projects/BUZZER_VOICE_SMOKE/inc/voice_synth.h` | 注释中的重载值同步 |
| `stc32g_sdcc/tools/voice/check_voice_model.py` | 周期预算常数改为**从 `common.h` 读 FOSC**，避免以后主频再调时静默算错 |

### 3.3 延时计数推导（SDCC 专用 asm 循环）

`Delay1000us_Reference` 是固定的 `MOV DR4 / DEC DR4,#1 / JNE` 循环，每次迭代 ≈4 个周期，时长随主频线性变化：

```
33.1776MHz： 33.1776e6 × 1e-3 / 4 ≈ 8293 次   （原值）
22.1184MHz： 22.1184e6 × 1e-3 / 4 ≈ 5529 次   （新值，取 0x1599）
Delay1us   ： 7 × 22.1184/33.1776 ≈ 4.67 → 取 5
```

与 STC 官方“延时函数生成器”在 22.1184MHz 给出的结果（`1ms=5528`、`1µs=4`、`10µs=54`、`100µs=551`）交叉校验：官方结果对应其 C 循环写法（同为 ≈4 周期/次），`5529` 与 `5528` 属 ±1 舍入差，一致。

> 注意：**不要**为了“对齐官方”把 SDCC 侧改回官方那种 C 循环——`common.c` 注释已记录该坑：SDCC 会把同样的 32 位循环展开成逐字节判断，得不到相同时长。

### 3.4 语音工程重载推导

`VOICE_SAMPLE_RATE_HZ = 7200`，Timer0 工作于 1T：

```
重载 = 65536 − FOSC/7200
33.1776MHz： 65536 − 4608 = 60928（原）
22.1184MHz： 65536 − 3072 = 62464（新）
```

### 3.5 明确不做的三件事

1. **不改 HID 烧录去写硬件选项**：应用固件启动会用 CHIPID 重新设频，选项频率必被覆盖，写选项零收益且有“误写选项导致芯片进不了下载模式”的风险；
2. **不改 STC-ISP 选项频率**：同上，仅文档说明同步更新，避免误导排查；
3. **不同步无线 IAP bootloader**：其波特率/延时同样依赖 FOSC，本次不在范围，列为遗留（若启用升级功能必须先同步到 22.1184MHz）。

## 4. 验证记录

### 4.1 构建
| 项 | 结果 |
|---|---|
| SDCC 全工程（16 个，含 HEX/MAP 布局校验） | **全部 PASS** |
| Keil `ROBOMASTER_INFANTRY` / `TEST` | **0 Error**（1 个无害 warning） |

### 4.2 故障板实测（SDCC 标定固件：`Board_Init()` → UART 230400 → 打时间标记）

| 项 | 期望 | 实测 |
|---|---|---|
| 串口 | 230400 可解 | 纯 ASCII 正常解出 |
| `T → 1` | 1000 ms | **1007.4 ms** |
| `1 → 2` | 3000 ms | **3022.8 ms** |
| `2 → 3` | 10 ms | **9.8 ms** |
| `3 → T` | 1000 ms | **1007.5 ms** |

结论：
1. **设频生效**：若 `System_Clock_Set()` 未执行（芯片仍按坏 CHIPID15 跑 ≈22.65MHz），按 22.1184 标定的延时应显示 ≈976ms 而非 1007ms；
2. **新延时计数正确**；
3. 存在 **+0.75% 系统偏差**，来自该芯片 22.1184MHz 档实际偏低约 0.75%（IRC 个体误差正常量级）；波特率误差 0.75% 远小于 8N1 的 ±4% 容差，对拓展板协议无影响。

## 5. 部署与后续

### 5.1 IDE 内置固件资产必须重新打包
- IDE 编译时用的固件源码来自**内置资产**：发布包 `<exe>/data/pieblock_runtime/{stc32g_sdcc,stc32g,vendor}`，以及部署到 `%APPDATA%\com.wpie\PIE-Block\runtime\sdcc\<fingerprint>\firmware`；
- 本次只改了仓库源码，**安装版 IDE 仍然用旧的 33.1776 资产**（实测 6 个已部署 fingerprint 的 `common.h` 全部还是 `33177600`）；
- 生效方式：重新 `flutter build windows --release`（见 `tools/package_flutter_windows.ps1`）后安装；
- **临时验证捷径**：`builder.dart` 支持 `PIEBLOCK_RUNTIME_ROOT` 环境变量（在该目录下找 `vendor/sdcc-toolchain` + `stc32g_sdcc` + `stc32g`）。可用目录联结指向仓库新源码后启动安装版 IDE，无需重新打包即可编译出新固件：
  ```powershell
  $env:PIEBLOCK_RUNTIME_ROOT='<repo>\tmp\runtime_root'
  & 'C:\Users\<user>\AppData\Local\Programs\PIE-Block\PIE-Block.exe'
  ```

### 5.2 筛板流程与工具需要按新标称更新
- 迁到 22.1184MHz 后，**关键校准项从 `CHIPID15` 变为 `CHIPID11`**；
- `tools/diagnostics/board_clock_screen.py` 的“230400 正常 = PASS”判据仍然成立（新主频下波特率依旧精确 230400），但其说明文字与“低档区间”解释需同步；
- `tools/diagnostics/board_clock_probe_report.py` 与探针固件的说明需注明“探针用于诊断 33.1776 档坏值；当前固件标称频率为 22.1184MHz”；
- 详见 [主控板主频异常筛板流程](../playbook/主控板主频异常筛板流程.md) 顶部的“现状更新”一节。

### 5.3 其他遗留
- 无线 IAP bootloader 同步 22.1184MHz（如果启用）；
- `docs/design/蜂鸣器LPC语音合成示例固件.md` 中 `33177600/4608 = 7200` 等表述同步；
- 本批故障板建议直接换片（校准数据损坏），22.1184MHz 迁移只是为了“让全系统不再依赖 33.1776 这一档”。

## 6. 回滚方案

所有改动集中在一次提交内，`System_Clock_Set()` 的 `case 33177600` 分支保留。回滚只需改三处：
1. `stc32g_sdcc/include/common.h` 与 `stc32g/Libraries/startup/inc/common.h` 的 `FOSC`；
2. 两套 `common.c` 里的 `#if (… == FOSC)` 守卫（SDCC 侧共 4 处）；
3. SDCC 延时两个立即数与语音 `VOICE_TIMER_RELOAD`。

## 7. 以后更改主频的检查清单

1. 两套 `common.h` 的 `FOSC`；
2. 两套 `common.c` 里**所有** `#if (… == FOSC)` 守卫（尤其 `Register_Set()` 那处，漏改会导致设频不执行）；
3. SDCC 延时 asm 计数按 `4 周期/次 × F × 时长` 重算，并用“帧间隔/时间标记”实测；
4. 语音工程 `VOICE_TIMER_RELOAD`（`65536 − F/采样率`）与 ISR 周期预算；
5. `tools/voice/check_voice_model.py` 预算（现已自动读 `common.h`）；
6. 诊断工具与筛板文档的“标称频率/候选波特率/判据”；
7. 构建 + 板测（波特率、3000ms 延时、语音听感）+ 全工程回归。
