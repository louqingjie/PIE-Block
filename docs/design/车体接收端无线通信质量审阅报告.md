## 4. 接收调度与帧处理

- 生成主循环顺序为 `nrf_handler()` → `ReadControllerInputs()` → 模式动作 → 两个扩展板 UART 帧（各约 1 ms + `Ms_Delay(5)`）→ `RemoteStatusSend()` → `Ms_Delay(10)`（[code_generator.dart](../../packages/pieblock_core/lib/src/code_generator.dart#L1649-L1673)）。按代码估算一圈约 22–28 ms，与遥控器 25 Hz（40 ms/帧）匹配。
- 车体 `nrf_handler()` 设计为一次轮询内排空 3 级 RX FIFO，方向正确；正常节奏下不会溢出。
- 车体回传 `RemoteStatusSend()` 每 5 圈发送一次（约 8–9 Hz），每次发送要切 TX 约 5 ms。
- **边界**：该工程的当前动作没有长阻塞；但生成器支持的其他配置可能加入阻塞动作（步兵的扳机 `Ms_Delay(trigger_time_ms)`、工程的摩擦轮斜坡 while 循环等）。3 级 FIFO 在 25 Hz 下只对应约 120 ms 缓冲，一旦阻塞超过该窗口就会丢包，而轮询式接收没有任何溢出检测/补救。

## 5. 问题清单

### 5.1 P0：断链失效保护缺失

**现象**

- 生成的主循环里没有任何“最近一次有效帧”的时间戳或超时判断；断链后 `rc_ctrl` 保持最后一次接收值，机器人继续按最后的摇杆/按键指令运行。
- 运行时里看似有一套 50 ms 超时，但它是**死代码**：
  - `remote_control_init()` 里 `PIT_Timer_Ms(TIM4, 1)` 被注释掉（[remote_control.c](../../stc32g_sdcc/libraries/boards/src/remote_control.c#L28)）；
  - 生成代码没有启用 TIM4，也没有调用 `remote_control_init()`；
  - 即使强行启用，`TM4_Isr()` 里的 `Clear_Time` 只在超时分支清零，收到有效帧时不清零（[remote_control.c](../../stc32g_sdcc/libraries/boards/src/remote_control.c#L130-L150)），逻辑本身也不正确。
- 这不是理论风险：遥控器进入管理员菜单时 `rc_mode` 被置为 `RC_CHECK`（[main.c](../../../remotecontrol/Code_User/main.c#L225)），而 `Rc_Send()` 只在 `RC_NORMAL` 时发送（[remote_control.c](../../../remotecontrol/Code_User/RC/remote_control.c#L108)）。**操作手在机器人通电/持握时打开菜单，遥控器立即停止发送，车体却继续执行最后指令。** 关遥控器、电池没电、超出距离同理。

**影响**

- 断链/停顿后机器人保持最后油门与转向，存在持续运动风险。
- 遥控器端虽有约 3 s 的链路故障显示，但显示不等于车体停车；车体侧没有任何本地保护。

**整改建议**

1. 在车体主循环/1 ms 时基维护 `last_valid_rx_tick`，由 `Rc_unpack_data()` 成功时刷新。
2. 超过约 120–150 ms（3–4 个 40 ms 帧周期）无有效帧时：清零 `rc_ctrl`、将电机/执行机构输出置安全值、点亮故障指示（LED/蜂鸣），并拒绝使用旧值。
3. 验收：运行中关闭遥控器、打开管理员菜单、遮挡/拉开距离，车体应在 150 ms 内停止并显示故障；恢复链路后能自动恢复。

### 5.2 P0/P1：运行时版本与频道一致性风险（部署阻断）

**现状**

- 仓库运行时已是 `0x27/0x15`（[nrf24l01.c](../../stc32g_sdcc/libraries/boards/src/nrf24l01.c#L123)），但**未提交**（`git status`：`M stc32g_sdcc/libraries/boards/src/nrf24l01.c` 等）；干净检出/其他机器会回到 `0x06/0x05`。
- 本机安装版 PIE-Block 1.9.0 的内置运行时仍是 `0x06/0x05`（1 Mbps）；仓库内 `build/windows/.../Release/data/pieblock_runtime` 的副本也仍是旧值。
- 工具链运行时查找顺序为：`PIEBLOCK_RUNTIME_ROOT` → 可执行文件旁 `data/pieblock_runtime` → 向上查找（[builder.dart](../../packages/pieblock_toolchain/lib/src/builder.dart#L899-L930)）。因此，除非显式设置 `PIEBLOCK_RUNTIME_ROOT` 指向更新后的运行时或重建安装包，默认构建仍可能产出 1 Mbps 车体固件。
- 仓库中最近可查的 `ROBOMASTER_ENGINEER` 构建产物（2026-11-27 16:59）使用的是模板配置 `Channal = 36`（[main.lst](../../stc32g_sdcc/build/ROBOMASTER_ENGINEER/main.lst#L4874-L4875)），并未看到当前 29 频道工程的构建产物。
- `tmp/runtime_root` 下的运行时副本已是 `0x27/0x15`，说明存在“用仓库运行时构建”的可行路径，但是否用于本次车体固件需要确认。

**影响**

- 如果车体实际烧录的是 1 Mbps 固件：遥控器 250 kbps 发送，车体完全收不到（不是丢包，是完全不通信）。
- 如果频道不一致（例如遥控器仍是旧频道 36）：同样完全不通信。
- 这两项会让“通信质量”讨论失去意义，必须先排除。

**整改建议**

1. 将 `stc32g_sdcc` / `stc32g` 的 `0x27/0x15` 修改提交，并纳入下一次应用打包的内置运行时。
2. 确认本次车体固件的构建来源：检查构建 `.asm` 中 `nrf24l01.c` 的源码路径和 `0x27` 常量，或读回车体 RF_SETUP；必要时设置 `PIEBLOCK_RUNTIME_ROOT` 指向仓库运行时后重编。
3. 用 `tools/rc_tool.py` 或遥控器菜单把遥控器频道设为 29，和车体生成代码一致；修改后回读确认。
4. 重新生成、编译并烧录车体固件，记录 hex 的 SHA-256 与构建时间，作为“已匹配”的证据。

### 5.3 P1：RX FIFO 状态位定义错误

车体 `nrf_handler()` 用 `FIFO_STATUS & 0x40` 判断 `RX_EMPTY`（[nrf24l01.c](../../stc32g_sdcc/libraries/boards/src/nrf24l01.c#L264)），但 nRF24L01+ 手册的位定义是：

- `RX_EMPTY = bit0`（`0x01`）
- `TX_REUSE = bit6`（`0x40`）

（规格书 FIFO_STATUS 表，p.61）

因此该循环的提前退出条件永远不成立，**每次都会读满 3 轮**：只有 1 个包时会额外读 2 次空 FIFO，把未定义数据喂给 `Rc_unpack_data()`；目前靠帧头（11）和校验和兜底，通常不会误动作，但流程错误、存在无谓 SPI 开销，也说明该驱动未逐位对照手册验证。建议改为 `0x01`，或按有效包计数控制循环；同时修复函数上方“RX_EMPTY (bit6)”的错误注释（[nrf24l01.c](../../stc32g_sdcc/libraries/boards/src/nrf24l01.c#L242-L247)）。

### 5.4 P1：接收质量不可观测

- `Rc_unpack_data()` 的返回值在 `nrf_handler()` 中被忽略，没有统计帧头错误、校验错误、RX FIFO 溢出、MAX_RT 等。
- 没有读取 `OBSERVE_TX` / `RSSI`，也没有把车体接收质量回传给遥控器。遥控器 RF 页显示的丢包/RTT 是**发送端 ACK 统计**，不等于车体真正处理成功的帧数（例如车体来不及取包时，ACK 仍可能由 nRF 硬件发出）。
- 初始化失败处理偏弱：`remoteControlInitWithTimeout()` 重试 20 次后**静默继续**，`StepDone(3)` 的成功提示音与失败没有区别；也没有像遥控器 `nrf_config_ok()` 那样对关键射频寄存器做回读校验。

**整改建议**：增加 RX 侧计数器（有效帧、帧头错误、校验错误、RX_FULL、MAX_RT、最近有效帧时间），并把关键量放进回传帧/调试串口/LED；初始化失败要有明确故障指示；周期回读 RF_SETUP/RF_CH 做自检。

### 5.5 P2：车体回传占用接收窗口

`RemoteStatusSend()` 每次回传的时序约为：`nrf_tx_mode()` 内 `Ms_Delay(1)` + 22 字节空口 + 固定 `Ms_Delay(3)` + `nrf_handler()`（[nrf24l01.c](../../stc32g_sdcc/libraries/boards/src/nrf24l01.c#L204-L240)、[nrf24l01.c](../../stc32g_sdcc/libraries/boards/src/nrf24l01.c#L299-L320)），即约 5 ms 不在 RX；回传约 8–9 Hz，约占 4% 时间。

- 正常 25 Hz 控制帧下，遥控器 5 次重发（2.5 ms）可吸收大部分影响。
- 但固定等 3 ms **不是最坏情况保证**：回传包若重发到 5 次（>3 ms），本次 `nrf_handler()` 看不到 `TX_DS/MAX_RT`，不会切回 RX，要等下一圈主循环（+10–15 ms）才恢复接收，弱链路下会放大丢帧。

**整改建议**：改为“等待 `TX_DS/MAX_RT` 的有界超时”，而不是固定 3 ms；或评估 ACK payload 方案（把 22 字节状态挂在遥控器控制帧的 ACK 上，避免车体主动切 TX）。至少应在回传失败后尽快切回 RX。

### 5.6 P3：清理项

- `remote_control.c` 仍保留旧 6 行协议 `RCPacket_Send()`、`TM4_Isr()` 和 `remote_control_init()` 的无限重试循环；当前生成代码不调用，但属于维护陷阱（一旦启用 TIM4 会与新的 22 字节回传协议冲突）。
- `nrf_link_check()` 注释写“0 成功、1 失败”，代码实际是 1 成功、0 失败（[nrf24l01.c](../../stc32g_sdcc/libraries/boards/src/nrf24l01.c#L142-L174)）。
- `NRF24L01_Init()` 仍打开 P2.6 EXTI（最高优先级），生成代码在初始化后关闭；`P2_INT_ISR_Handler()` 中若 P2.6 标志残留会调用 `nrf_handler()`。当前没有其它 P2 EXTI，暂无冲突，但建议初始化后清除该 EXTI 标志或不再打开。
- 文档漂移：遥控器 README 说车体使用 Ci24R1，而生成的车体代码实际使用 nRF24L01+ 四线 SPI 驱动；建议统一为实际硬件（nRF24L01+）。

## 6. 整改与验收顺序

| 优先级 | 整改项 | 验收方法 |
| --- | --- | --- |
| P0 | 车体断链失效保护 | 运行中关遥控器 / 打开管理员菜单 / 遮断天线：车体应在 120–150 ms 内停转并显示故障；恢复后自动恢复 |
| P0 | 运行时版本与频道一致 | 构建 `.asm` 中 `nrf24l01.c` 来自更新运行时且含 `0x27/0x15`；遥控器与车体频道均为 29；记录车体 hex 的 SHA-256 |
| P1 | 修正 FIFO_STATUS 位并加统计 | 单元/台架验证只取有效包；注入帧头/校验错误、RX_FULL，统计计数正确 |
| P1 | 接收质量可观测 | 长跑 10 min 以上，同时记录遥控器 ACK 丢包、车体有效帧/错误/溢出计数，二者偏差可解释 |
| P2 | 回传时序 | 弱信号/高重发场景下，车体回传失败后能及时回到 RX；控制帧丢失率不因回传而显著上升 |
| P3 | 清理死代码与错误注释 | 代码审查通过，README 与实现一致 |
